# Control-plane database identities

The PostgreSQL bootstrap creates one schema-owner login (`control`) for the
one-shot migration process and distinct non-owner runtime logins for the API,
each worker class, the backup scheduler and the development driver ledger.
Migration `0017_runtime_database_privileges` grants only the object operations
needed by each process. All runtime roles lack `SUPERUSER`, `CREATEDB`,
`CREATEROLE`, `REPLICATION`, `BYPASSRLS`, schema creation and audit mutation.

Credentials are generated by `deploy/bootstrap-local-env.sh` as read-only files
inside a mode-0700 local directory. The mode-0600 environment file contains only fixed
`@/run/secrets/...` references, and Compose mounts each file into exactly the
processes named by the configuration matrix. CI renders recognizable canary
credentials and fails if their values enter either Compose model. Production
issues equivalent references from the approved secret manager. The
security owner sets the maximum credential lifetime before production approval;
until then, production personal data remains prohibited.

Normal rotation is additive: issue a second credential for the same privilege
role, update and verify the new process pool, drain old connections, then revoke
the old login. On suspected compromise, revoke the affected login immediately,
stop its queue, rotate every provider credential visible to that process and
review its command, operation and audit records before resuming. Passwords,
password hashes and rendered database URLs must never enter Git, rendered
Compose output, logs, support bundles or infrastructure plan fixtures.

The development Docker driver applies the same rule to dynamically created
containers. Each short-lived database, release or recovery job receives a
random, read-only volume subpath containing only that job's credentials;
Docker `Env` and `Cmd` contain file paths and shell variable references, never
values. Job files are atomically written, deleted after container cleanup, and
stale UUID-scoped directories are removed at fail-closed driver startup.
Long-lived Paperless and release-runtime containers use dedicated read-only
subpaths in the driver-only secret volume and file-backed settings.
Odoo bridge tokens and Paperless client tokens use separate worker-facing
volumes; only membership and invoice workers receive the Paperless client
volume, read-only. Configuration digests version the long-lived mount boundary
so migration replaces stale containers before deleting legacy secret files.
